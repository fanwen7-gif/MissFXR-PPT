为什么不得不这么想？

当你只有一个 Agent，你可以偷懒——先做第一步，做完了再想第二步。

当你要同时分配任务给 3 个 Agent，你必须提前想清楚三件事。工具的并行逻辑，把你的思维也逼成了并行。

这不是做事顺序的变化——是从「局部最优」到「全局最优」的决策方式升级。

🗺️

规划者

Orchestrator
拆任务、分工作 ▶
  • 把大任务拆成若干子任务
  • 决定每个子任务分给哪个 Agent
  • 整合所有结果，发现冲突
  • 遇到问题时重新调度
Orchestrator 不是魔法，是你的思维被编码进去的地方。多 Agent 真正逼你做的事：开跑之前先想清楚怎么拆——这才是思维升级的来源。
→ 通常是你，或者主控 Agent
⚡

执行者

Worker Agents
并行处理子任务 ▶
  • 专注做好一件具体的事
  • 不管其他 Agent 在做什么
  • 可以同时有 2–10+ 个并行
  • 完成后把结果交回给规划者
→ 数量越多，并行越强，速度越快
🎯

整合者

Synthesizer
合并结果、校验一致 ▶
  • 把多个 Agent 的输出合并
  • 发现不一致或互相矛盾的地方
  • 生成最终统一结果
  • 判断是否需要重跑某个子任务
→ 质量的最后一道关卡

什么任务才真正适合多 Agent？

不是所有任务都适合并行——用错了比单 Agent 更乱。

✓ 适合并行
子任务互相独立，不依赖彼此的输出
需要从不同视角审视同一个问题
单个 Agent 的 context 放不下整个任务
✗ 不适合并行
步骤 B 必须等步骤 A 的结果才能开始
任务本身很小，拆开反而多了传递成本
⚠ 反例

「分析反馈 → 诊断问题 → 设计方案」看起来像并行，其实是串行——方案依赖诊断，诊断依赖数据。强行并行只会让三个 Agent 在错误前提上各自跑偏。

⚠️ 反直觉

3 个容易踩的坑

多 Agent 不是银弹，用不好会比单 Agent 更混乱。

🪞

结果互相矛盾

不同 Agent 可能从同一数据得出相反结论。你是规划者，要负责仲裁——没有仲裁就没法合并。

对策：加一个整合 Agent 专门做一致性校验
📦

上下文在传递中丢失

Agent 之间传信息，细节会丢。越往后的 Agent，越可能在不准确的前提上工作。

对策：规划阶段写清楚「共同上下文」，每个 Agent 都读
🌀

没想清楚就开跑

多 Agent 会放大规划质量。想清楚了，结果翻倍好；想模糊了，N 个 Agent 一起跑偏，代价更大。

对策：先花 10 分钟写清楚目标 + 子任务边界，再启动
📁 真实案例

一次「X 功能」的战略级重构

同一个任务——梳理某功能积累的 160 条用户反馈、重做整套系统的战略规划——两种工作方式的对比。

1
导出 160 条 case，开始整理 → 才发现：3 套系统各记各的，格式全不一样，光清洗数据就要半天
2
开始做分类整理 → 才发现：建议和 bug 混在一起，没法分开统计，分类体系要重做
3
想设计新的字段结构 → 才发现：数据来源不止 2 个渠道，原来的设计要推倒重来
4
想加自动化 → 才发现：负责人 / 处理进度 / 反馈来源这些关键字段根本不存在，自动化没有基础
❌ 每次「才发现」都是一次返工。走到第 4 步，已经不知道第 1 步要不要重做了。
A
现状分析 统计 160 条分类分布、渠道来源、字段填写率、处理状态——全部同步产出
B
问题诊断 4 大痛点（无全渠道聚合 / 分级形同虚设 / bug 建议混杂 / 处理闭环全空）同时找到
C
方案设计 三层结构（采集层 → 分类分级层 → 处理闭环层）整体设计，不分先后
↓ 三路同时开跑，完成后收口到一起
整
规划者整合：一次性看全貌 同时拿到三份结论 → 发现「3 套并 1 套」是根本解 → 设计 22 字段新表 → 全局最优，不是局部最优
✓ 先看全地图，再踏出第一步。方向定了，执行才不会偏。
